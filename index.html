SDK Integration & Customization via Callback

A manual integration approach that gives development teams greater flexibility: use the IronSKY SDK's callback mechanism to handle security events directly in the app, in real time.

Method: SDK callback Latency: real-time Audience: development team

Overview

Beyond storage-based log forwarding, SecIron also offers manual SDK Integration that gives application development teams greater flexibility. With this approach, developers use the callback mechanism provided by the IronSKY SDK to handle security events directly in the app, without waiting for the export/pull process.

By receiving events as they occur, the app can forward them to an external system, in particular a SIEM, in real time for monitoring and incident correlation.

Callback Mechanism

The app registers a callback for the RISKEVENT type. Each time IronSKY detects a threat, the callback is invoked with the event details as JSON. The following call order is mandatory:

initialization order (Android)
1. registerService(callback, Type.RISKEVENT, 0.5)   // register the callback first
2. registerService(callback, Type.DEVINFO, 0.5)      // device fingerprint (udid)
3. setUserId(context, userId)                        // associate a user id
4. initAppsecEverisk(context, LICENSE_KEY)           // initialize last
ImportantregisterService must be called before initAppsecEverisk. If reversed, the callback will never fire.

Event Structure

The object received by the RISKEVENT callback includes, among others:

example callback payload
{
  "key": "event_risk_root",           // security event type
  "name": "Root Detected",
  "riskLevel": "high",                 // low | medium | high
  "responseType": 1,                   // RASP action
  "responseI18n": "[{...localized message...}]",
  "eventId": "1141###<udid>###...###event_risk_root",
  "time": 1789828899241
}
FieldDescription
keySecurity event type (root, injection, MITM, and others).
nameShort event name.
riskLevelRisk level: low, medium, or high.
responseTypeResponse action code recommended by the SDK.
responseI18nLocalized response message (title, body, button).
eventId / timeUnique event identifier and time of occurrence.

Use Case: Server Forwarder (Realtime to SIEM)

The app forwards each callback event to a client-owned server forwarder, which normalizes and relays it to the SIEM in real time. The forwarder is built and run on the client side.

   Mobile App + IronSKY SDK          Server Forwarder (client)          SIEM
        callback RISKEVENT  ── POST ─▶  receive + normalize  ────▶  rules → alert

1. App Side

Inside the callback, build the payload and send it via HTTP POST to the forwarder endpoint. Run it on a background thread so the UI is not blocked. The deviceUdid value comes from the DEVINFO callback (see the initialization order).

Kotlin — forward the event from the callback
val payload = JSONObject().put("ironsky", JSONObject()
    .put("security_event", ev.optString("key"))
    .put("risk_level", ev.optString("riskLevel"))
    .put("udid", deviceUdid)
    .put("event_time", ev.optLong("time")))

Thread {
    val c = URL("https://forwarder.internal/ironsky").openConnection() as HttpURLConnection
    c.requestMethod = "POST"; c.doOutput = true
    c.setRequestProperty("Content-Type", "application/json")
    c.setRequestProperty("Authorization", "Bearer <TOKEN>")
    c.outputStream.use { it.write(payload.toString().toByteArray()) }
    c.inputStream.close()
}.start()

2. Server Forwarder (reference implementation)

The forwarder receives the event, verifies the token, then writes it to the location the SIEM reads. Minimal example in Python:

forwarder.py
from flask import Flask, request, abort
import json

app = Flask(__name__)
OUT = "/opt/ironsky/out/events.jsonl"   # location read by the SIEM

@app.post("/ironsky")
def ingest():
    if request.headers.get("Authorization") != "Bearer <TOKEN>":
        abort(401)
    ev = request.get_json(force=True, silent=True) or {}
    with open(OUT, "a") as f:
        f.write(json.dumps(ev, ensure_ascii=False) + "\n")
    return ("", 204)

3. SIEM Side

The SIEM reads the forwarder's output as JSON logs, the same as in the S3 method, so the same rules apply. Wazuh example:

/var/ossec/etc/ossec.conf
<localfile>
  <log_format>json</log_format>
  <location>/opt/ironsky/out/events.jsonl</location>
</localfile>
NoteKeep the payload schema consistent with the S3 method (wrap it under ironsky, e.g. ironsky.security_event) so the same SIEM rules/correlation apply to both methods. Run the forwarder behind HTTPS and use an authentication token.

Implementation Notes

  • Perform network sending on a background thread so the UI is not blocked.
  • The callback's key value is identical to the Security event field in the S3 method, so the same SIEM correlation rules apply to both.
  • Forwarding to the SIEM via a server forwarder is covered in the Use Case: Server Forwarder section above.
